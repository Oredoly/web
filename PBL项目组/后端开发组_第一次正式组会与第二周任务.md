# 后端开发组第一次正式组会与第二周任务安排

> 适用时间：第一次正式组会当天起的一周（组会时间：明天 10:00-11:00）
> 背景：全组对后端开发 0 基础，包括 Git。第一周已分为开发组和顾问组，开发组调研类似项目/网站，顾问组做产品需求粗略调研。
> 本周目标：把第一周调研收敛成 MVP 范围；所有人把开发环境跑通；完成第一次 Git 协作；第二周结束时能演示“需求是什么、系统怎么跑、协作怎么做”。

## 一、第一次正式组会设计

### 1. 会前准备

所有人需要在组会前完成：

- 每位成员准备 2-3 分钟的展示，允许直接用浏览器打开调研对象，不必做正式 PPT。
- 开发组成员重点展示“网站是什么、核心功能、我们能学什么、第一版不做”。
- 顾问组成员重点展示“用户是谁、使用场景、必须功能、待确认问题”。
- 每位成员会后把展示要点提交到共享文档，负责人统一汇总。
- 开发组：整理 3 到 5 个类似项目/网站，不追求讲得多，只讲“结论”。
- 顾问组：整理第一版需求结论，区分“必须做、先不做、待确认”。
- 负责人：提前建好共享文档，包括《需求池》《本周任务表》《学习记录》。
- 负责人：准备一个 Git 演示仓库或空仓库，组会现场演示提交和拉取。

建议各组在组会前 1 天提交一页汇总，避免现场临时翻资料。

### 2. 开发组汇报模板

每个调研对象按以下格式汇报：

| 字段 | 要写清楚的内容 |
| --- | --- |
| 网站/项目名称 | 一句话说明它是什么 |
| 核心功能 | 它主要解决什么问题 |
| 用户角色 | 哪些人使用 |
| 主要流程 | 用户进去后做什么 |
| 技术栈 | 能看出的技术、平台或框架 |
| 值得借鉴 | 页面、功能、流程、数据结构中能借鉴的点 |
| 不建议照搬 | 哪些东西对 0 基础团队太重 |

汇报标准：听完后，大家能说出“这个网站有哪些功能值得我们做，哪些我们第一版不做”。

### 3. 顾问组汇报模板

按以下角度汇报：

| 字段 | 要写清楚的内容 |
| --- | --- |
| 目标用户 | 管理员、教师、学生、中小学老师等 |
| 使用场景 | 用户在什么时候、做什么事 |
| 核心痛点 | 没有这个系统时会遇到什么问题 |
| 必须功能 | 第一版没有它就跑不通的流程 |
| 可后补功能 | 可以放到第二版或以后的功能 |
| 待确认问题 | 需要和课程组、新媒体组、成果转化组确认的问题 |

汇报标准：听完后，能直接圈出 P0 功能，而不是得到一个“什么都要做”的清单。

### 4. 会议流程建议

建议按实际组会时间 10:00-11:00，共 60 分钟执行：

| 时间 | 环节 | 目的 | 关键产出 |
| --- | --- | --- | --- |
| 10:00-10:12 | 各成员汇报并展示 | 快速知道每个调研对象 | 《可借鉴功能清单》《需求清单 v0.1》 |
| 10:12-10:28 | Brainstorm 网站需求 | 收敛成“第一版做什么” | P0/P1/P2 需求池 |
| 10:28-10:36 | 划分模块并分工 | 让每个人知道下周负责什么 | 《本周任务表》和模块负责人 |
| 10:36-10:50 | Git/GitHub 演示 | 完成第一次版本控制认知 | 全员知道 clone/add/commit/push/分支/合并请求 |
| 10:50-10:55 | 老师补充 | 收集外部意见 | 补充意见记录 |
| 10:55-11:00 | 交流答疑 | 解决疑问并明确下一步 | 未决问题负责人清单 |

### 5. 组会主持脚本

1. 各成员汇报：
   - 每人 2-3 分钟，先打开一个网站，说“它解决什么问题”，再讲“我们可以学什么、第一版不做”。
   - 负责人把高频功能写到共享白板，重复功能合并，不打断、不辩论。
2. Brainstorm 需求：
   - 只回答三个问题：第一版给谁用？一次完整流程是什么？哪些功能先不做？
   - 结束后当场把需求标成 P0、P1、P2，不接受“以后再说”留在未决清单。
3. 模块分工：
   - 按模块分工，不按技术分工；每个人至少认领一个模块的调研或开发任务。
   - 分工表当场填写：模块、负责人、支持人、交付物、完成时间。
4. Git/GitHub 演示：
   - 现场演示创建仓库、克隆、修改、提交、推送、分支和合并请求。
   - 当场布置第一个 Git 练习：每个人把名字加到成员列表并提交。
5. 老师补充：
   - 记录意见，会后由负责人逐条映射到需求池或任务表。
6. 交流答疑：
   - 只解决影响下周开工的问题；不能当场解决的问题，写明负责人和确认时间。

## 二、第一次正式组会上要统一的结论

### 1. MVP 范围

建议第一版只做以下 P0 功能：

| 模块 | 说明 |
| --- | --- |
| 用户登录与角色 | 管理员、教师、学生、执行导师等基础角色 |
| 学校与班级 | 学校、班级、学生信息的录入和维护 |
| PBL 课程 | 课程、课时、任务、课程资源的基础管理 |
| 学生作品 | 学生上传作品、查看作品、展示作品 |
| 成长档案 | 记录过程、生成和导出档案 |
| 基础数据看板 | 学校数、学生数、课程数、作品数等简单统计 |

第一版不需要做：

- AI 个性化推荐
- VR/3D 场景交互
- 小程序和移动端适配
- 复杂权限体系
- 微服务架构
- 大数据分析
- 完整商业化后台

### 2. 一次完整使用流程

第二周结束时，理想情况下可以用一句话说明系统：

> 管理员创建学校和班级，导入学生；老师创建 PBL 课程并布置任务；学生加入课程、记录过程并提交作品；老师查看作品并评价；最后导出学生成长档案。

这个流程就是第二周的“北极星”，所有任务都要服务它。

### 3. 技术路线建议

推荐采用已经存在的项目栈：

- 后端：Node.js + Express
- 数据库：SQLite（better-sqlite3）
- 页面：EJS 服务端渲染
- 本地数据库文件：不需要单独安装数据库服务

理由：

- 本团队已有可参考的后端原型，代码在 `C:\Users\nmg2333\Desktop\project\backend`。
- 这套技术栈对 0 基础队伍相对简单：一个命令启动，一个文件就是数据库。
- 先不引入 React/Vue，避免第一周同时学习前端框架和后端。
- 现有项目已经有用户、课程、作品、成长档案等模块，可以作为“真实教材”。

如果确认不从现有项目继续，第二周改为：

- 开发组先搭一个“Hello World”网页服务。
- 再加一个页面。
- 再加一张表和一个增删改查接口。
- 顾问组继续补需求和页面流程。

## 三、Git 协作规范

### 1. 第一周只需要掌握的 Git 概念

| 概念 | 一句话解释 |
| --- | --- |
| 仓库 | 保存所有代码和历史记录的地方 |
| 提交 commit | 给当前代码保存一个版本 |
| 分支 branch | 在独立线路上改代码，不影响主分支 |
| 拉取 pull | 把别人最新的代码下载到本地 |
| 推送 push | 把自己本地的提交上传到远端 |
| 合并请求 PR/MR | 申请把自己的改动合并到主分支 |

### 2. 常用命令

第一周只需要熟练这几个命令：

```bash
git clone <仓库地址>
git status
git add .
git commit -m "说明这次改了什么"
git pull
git push
git switch -c dev/姓名/任务
```

不要求第一周学会解决复杂冲突。遇到冲突时找负责人，不要自己乱删代码。

### 3. 小组协作规则

- `main` 分支保持可用，不直接往 `main` 提交。
- 每人按任务建分支，命名示例：`dev/张三/课程列表`。
- 每次提交只做一件小事情，提交信息写清楚，例如 `新增课程列表页面`。
- 完成一个任务后发起合并请求，由负责人或另一位成员检查后再合并。
- 每天开始写代码前先 `git pull`。
- 禁止 `git push --force`。
- 不把数据库文件、`.env`、`node_modules` 提交到仓库。

## 四、第二周具体任务

### 周一：环境准备与调研收口

| 组别 | 任务 | 验收标准 |
| --- | --- | --- |
| 全员 | 安装 Node.js LTS、VS Code、Git，注册代码托管平台账号 | 能执行 `node -v` 和 `git --version`，提交安装截图 |
| 开发组 | 把第一周调研整理成《可借鉴功能清单》 | 至少 5 个借鉴点，每个说明对应到哪个模块 |
| 顾问组 | 把粗略调研整理成《需求清单 v0.1》 | 有用户角色、核心场景、必须功能、待确认问题 |
| 负责人 | 建共享文档、建仓库、邀请成员 | 全员能访问文档和仓库 |

### 周二：Git 第一次实战

| 组别 | 任务 | 验收标准 |
| --- | --- | --- |
| 全员 | 克隆仓库，把自己的名字加到成员列表，建分支并提交 | 每个成员完成一次 `clone -> add -> commit -> push -> 合并请求` |
| 开发组 | 把现有后端跑起来，记录安装和启动过程 | 浏览器能看到登录页，写出一页《启动手册 v0.1》 |
| 顾问组 | 给管理员、教师、学生各写 2 到 3 个用户故事 | 每个用户故事包含“谁、在什么场景、做什么、为什么” |

### 周三：读懂系统怎么工作

| 组别 | 任务 | 验收标准 |
| --- | --- | --- |
| 开发组 | 阅读 `app.js`、`routes`、`controllers`、`views`、`database/schema.sql` | 能画出“浏览器请求 -> 路由 -> 控制器 -> 数据库 -> 页面”的流程 |
| 开发组 | 写一页《这个网站是怎么跑起来的》 | 新人看完后能解释请求从哪里进、数据存在哪里 |
| 顾问组 | 把《需求清单 v0.1》升级成 P0/P1/P2 需求池 | 每个需求有优先级、功能说明、验收标准 |
| 顾问组 | 画出第一版页面导航图 | 能说清登录后进入哪些页面、每个页面干什么 |

### 周四：第一次小功能开发

| 组别 | 任务 | 验收标准 |
| --- | --- | --- |
| 开发组 | 每人或每组完成一个很小的代码改动 | 例如新增 `/health` 接口或“后端开发组”页面，功能能运行 |
| 开发组 | 走完一次合并请求流程 | 改动通过负责人检查并合并到 `main` |
| 顾问组 | 补充关键页面需要的字段 | 学生、课程、作品、成长档案各列出必要字段 |
| 顾问组 | 整理待确认问题清单 | 每个问题都写明“谁去确认、什么时候确认、影响哪个模块” |

### 周五：交付与第三次组会准备

| 组别 | 任务 | 验收标准 |
| --- | --- | --- |
| 全员 | 更新本周任务表和共享文档 | 所有任务都有状态、负责人、完成证据 |
| 开发组 | 准备 3 分钟演示 | 能现场跑起系统，演示登录页和一个小改动 |
| 顾问组 | 准备 3 分钟需求汇报 | 能讲清 P0 流程、页面导航、待确认问题 |
| 负责人 | 检查全部交付并规划第三次组会 | 形成第三周任务草案和风险清单 |

## 五、第二周结束验收清单

第二周结束时，团队应能回答这 5 个问题：

1. 第一版给谁用？第一次完整使用流程是什么？
2. 哪些功能是 P0，哪些明确不做？
3. 所有人是否都能在本地跑起系统？
4. 是否所有人都完成了一次 Git 协作？
5. 下周是否有一个可继续开发的最小代码骨架？

## 六、给负责人的执行建议

- 每天只做 10 分钟快速同步，不组织长会，群里用固定格式更新：今天做了什么、卡在哪里、明天做什么。
- 0 基础成员先追求“跑通”，不要追求“写对”。第一周能跑通项目就是巨大胜利。
- 开发组如果卡在 Git，先只教 `pull`、`commit`、`push`，其他命令第三周再补。
- 顾问组不要继续无限调研，第二周必须收敛成需求和页面，否则后面开发无法开工。
- 所有产出都放进共享文档或仓库，避免第二周结束后资料仍然散落在聊天记录里。
